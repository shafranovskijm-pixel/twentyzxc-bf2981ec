# Файлы ФИС ФРДО и собственные подпись/печать в MCP 0.9.0

В плагине добавлены доступ к восьми существующим оригиналам из раздела ФРДО, подготовка и отдельная отправка выбранного пакета, получение собственных изображений подписи/печати и их наложение на приложенный PDF. Обычные договоры, счета и акты, доступы ФРДО и их текущие инструменты сохраняют свои отдельные пути.

## Исходные файлы и отправка

`crm_list_frdo_templates` возвращает зарегистрированные ID, версии, SHA256, размеры, MIME и ссылки: инструкция DOCX, приказ DOCX, уже готовый приказ PDF, соглашение PDF, четыре XLSX ДПО/ПО. Датированные образцы 06.11.2023 предоставляются с исходными названиями, без утверждения об актуальности требований. `crm_get_frdo_template` проверяет точные байты оригинала. Не нужно пересоздавать файлы из распознанного текста или превращать таблицы в PDF.

Для письма выберите организацию через поиск и чтение карточки. `crm_prepare_frdo_package` требует точные clientId, ожидаемые ИНН и версию карточки, а также выбранные ID/версии/SHA256. При неоднозначной организации или неизвестном выборе ДПО/ПО уточните намерение пользователя. Новый постоянный email сначала сохраните в карточку; разовый адрес укажите явно. Если адрес не передан, используется email карточки. По умолчанию берётся существующий текст инструкций раздела ФРДО; можно передать согласованные тему и текст.

Подготовка сохраняет адресата, текст и неизменяемые копии исходных вложений в закрытом Storage, проверяя зарегистрированные хеши. Пользователю показываются весь комплект, получатель и временные ссылки. Подготовка ничего не отправляет. `crm_send_frdo_package` вызывается только после отдельного подтверждения показанного письма с точными deliveryId/expectedRecipient. Пожелание добавить возможность отправки не является командой отправить письмо.

`crm_get_frdo_package_delivery` читает журнал и обновляет ссылки. Один requestId относится к одному неизменному запросу; повтор одинаковой команды возвращает прежнюю операцию. `prepared` не означает отправку. `smtp_accepted` подтверждает только принятие SMTP-сервером. При `sending`/`unknown` нельзя автоматически создавать новый запрос и повторять письмо. Для намеренной повторной отправки подготовьте новый комплект, покажите его и получите новое подтверждение.

Новый outbox отделён от финансовых документов. Произвольные URL/файлы нельзя подставлять вместо зарегистрированных исходников. Старые проверки банковских реквизитов и подготовка PDF договоров/счетов/актов не ослабляются. Восьмой PDF доступен по исходному Lovable asset URL; это существующий оригинал, а не нарисованная подпись для переноса.

## Подпись, печать и отдельный PDF

`crm_get_company_document_assets` возвращает только существующие PNG исполнителя: `/images/signature.png` и `/images/stamp.png`, их хеши, размеры и ссылки. Изображения не перерисовываются. В договорах, счетах и актах CRM они уже вставляются в блок исполнителя; для custom-текста используется `{{company.signature}}` отдельной строкой. Блок подписи заказчика не заполняется изображением исполнителя.

Для приложенного PDF сначала передайте исходное вложение через файловый параметр `crm_inspect_pdf_for_signing`. Инструмент возвращает SHA256 и геометрию страниц; он не определяет место подписи по одним размерам. Прочитайте/покажите исходник и уточните неоднозначное размещение.

`crm_apply_company_marks_to_pdf` получает тот же исходник, его ожидаемый SHA256, хеши использованных изображений и явные placements. Страница нумеруется с 1; x/y — нижний левый угол изображения в PDF points (1/72 дюйма), начало координат внизу слева страницы. Порядок записей задаёт порядок наложения. Все изображения должны помещаться внутри выбранных страниц. Поворот затронутой страницы и электронно подписанный PDF обрабатываются как неподдерживаемые исходники: нужен исходный файл без ЭЦП/поворота.

Создаётся отдельная неизменяемая копия; исходный файл не меняется, письмо не отправляется. Ответ содержит artifactId, метаданные исходника/результата и временную ссылку. `crm_get_signed_pdf` повторно открывает эту копию и обновляет ссылку. Один requestId не используется для разных файлов, изображений или координат. Ссылки/токены оригинального вложения не сохраняются в метаданных.

Это наложение факсимильных изображений, не криптографическая подпись, не КриптоПро и не подтверждение подписания заказчиком. Существующие PNG остаются в их текущем формате хранения; новый инструмент не меняет настройки доступа или сами изображения.

## Граница сервера и проверка

Все MCP операции проверяют JWT и существующую admin-роль. Email worker повторяет эти проверки до Storage/worker RPC; его служебные операции ограничены новым outbox. Клиентская карточка читается только безопасной проекцией без логинов, паролей и закрытых заметок. Для всех новых файлов используется существующий закрытый bucket `contracts`; публичный bucket останавливает операции.

Миграция `20261021010000_crm_frdo_documents.sql` регистрирует точный каталог, отдельный журнал ФРДО и метаданные производных PDF. Она не меняет реальные карточки, доступы, роли, тарифы или текущую отправку финансовых документов. Проверьте unit tests, реальный PGlite SQL runner `npm run test:crm:frdo-documents:sql`, TypeScript, линтер и сборку/манифест. Проверки SMTP выполняются с подменённым transport и не отправляют реальную почту. Синтетические SQL проверки полностью откатываются.

При выпуске примените миграцию, разверните `crm-frdo-email`, опубликуйте MCP и обновите инструменты подключения. Проверяйте не только наличие имён, но и fileParams для inspect/apply и ранее существующих import tool. Платформа может перегенерировать MCP, потеряв исправление SDK для файловых параметров; перед выпуском сохраняйте проверенный runtime. Различайте локальные проверки, живую SQL-проверку, каталог подключения и реальную отправку — последняя не требуется для проверки выпуска и без отдельного разрешения не выполняется.
