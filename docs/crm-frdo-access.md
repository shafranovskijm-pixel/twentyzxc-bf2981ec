# Доступы ФИС ФРДО через плагин CRM

MCP 0.8.0 добавляет три операции в существующий плагин 24ZXC:

- `crm_get_frdo_access_status(clientId)` — наличие логина, пароля ДПО и пароля ПО, организация, ИНН и версия карточки.
- `crm_compare_frdo_access(clientId, expectedInn, credentials)` — сверка только переданных значений без записи.
- `crm_update_frdo_access(requestId, clientId, expectedRevision, expectedInn, changes)` — запись только переданных полей в существующую карточку.

Это расширение инструментов и инструкций существующего MCP-сервера. Изменение локального кеша плагина само по себе не публикует эти возможности.

## Работа в разговоре

Найдите организацию через `crm_search_clients` по ИНН или названию. Выберите конкретный `clientId`; при неоднозначном результате спросите пользователя. Не ищите организацию по паролю и не переносите доступы между похожими карточками. Перед записью прочитайте карточку или статус доступов и используйте текущий `crm_revision`.

`expectedInn` обязателен: точный ИНН выбранной карточки или `null`, если ИНН в ней отсутствует. Неверный ИНН останавливает сверку и запись. Это проверка связи с выбранной карточкой, а не проверка организации в государственном реестре. Если ИНН отсутствует, пользователь должен однозначно выбрать организацию по другим предоставленным реквизитам.

Поля `login`, `passwordDpo`, `passwordPo` соответствуют существующим `clients.frdo_login`, `frdo_password`, `frdo_password_po`. ДПО и ПО различаются: не копируйте один пароль в оба поля без указания пользователя. Если тип неизвестен, уточните его. Значения сохраняются буквально, включая пробелы по краям. Пустые строки, строки только из пробелов и управляющие символы отклоняются. Логин ограничен 500 символами, каждый пароль — 4096.

Пропущенное поле не меняется. `null` допускается только при записи и означает явную очистку указанного поля. Не передавайте `null`, если пользователь просто не сообщил значение. При конфликте версии перечитайте карточку и пересмотрите правку; не подставляйте новую версию автоматически. Повтор потерянного ответа использует тот же `requestId` и неизменную команду. Для новой правки нужен новый UUID. `replayed:true` возвращает историческую квитанцию исходной операции: после более поздних правок актуальное состояние нужно прочитать или сверить отдельно.

Сверка возвращает для каждого переданного поля `match`, `different` или `not_set`. Она сравнивает значения с CRM, не входит во внешнюю ФИС ФРДО и не доказывает действительность пароля. Не перебирайте варианты. В ответе пользователю указывайте организацию, результат сверки/названия изменённых полей и версию. Не перепечатывайте логины и пароли в чате, документах, заметках или именах файлов.

Примеры запросов без реальных секретов: «Сохрани предоставленные доступы ФРДО для организации с указанным ИНН»; «Сверь предоставленные пароль ДПО и логин с выбранной карточкой». Сначала уточните отсутствующие данные, а не подставляйте примерные значения.

## Граница защиты

Все операции используют JWT проверенного пользователя и существующую роль администратора; RPC повторно проверяют роль. Новые права OAuth, обход RLS и service-role доступ не требуются. Обычные поиск и чтение клиента по-прежнему не возвращают учётные данные.

SQL и TypeScript возвращают только разрешённые поля: идентификаторы/реквизиты выбранного клиента, признаки наличия, результат сверки, названия изменённых полей и подтверждение операции. Ошибки имеют фиксированные сообщения. При записи используется отдельный закрытый журнал: метаданные и медленный солёный отпечаток команды для проверки повторов, без открытых логинов/паролей и без копии `changes` в обычном журнале карточек. Существующие значения в `clients` продолжают использовать текущий формат CRM; эта доработка не мигрирует их в хранилище зашифрованных секретов.

Введённые в чат значения и аргументы вызова инструмента могут оставаться в истории клиента и инфраструктуре платформы. Запрет на эхо в ответах и журнале CRM не является гарантией удаления этой истории. Не запрашивайте реальные пароли для разработки или проверки выпуска. Если пользователь не хочет передавать секреты через чат, он может заполнить существующие поля в карточке CRM напрямую; плагин затем покажет только признаки их наличия.

## Проверка и выпуск

Примените `supabase/migrations/20261019010000_crm_frdo_credentials.sql` перед публикацией нового MCP bundle. Миграция не меняет существующие доступы клиентов, роли или тарифы. Она проверяет доступность `pgcrypto` для отпечатка команд.

Проверки: `npm run test:crm`, `npm run test:crm:sql`, `npm run test:crm:frdo:sql`, TypeScript приложения и сборочных инструментов, затем `npm run build` и `npm run mcp:manifest`. Новые unit/SQL проверки используют вымышленные доступы, в том числе различающиеся пароли ДПО/ПО, точные пробелы, явную очистку, неверный ИНН, конфликт версии и повторы команд. PGlite выполняет настоящий PostgreSQL/pgcrypto; это не проверка развёрнутой инфраструктуры.

Зафиксируйте исходники, сгенерированный `supabase/functions/mcp/index.ts` и `.lovable/mcp/manifest.json`, примените миграцию, разверните только функцию `mcp`, затем обновите список инструментов подключения ChatGPT/Codex. Автоматические разрешения плагина не расширяются. Проверка без авторизации должна по-прежнему давать OAuth challenge. Наличие нового имени в манифесте ещё не подтверждает вызов через подключённый клиент.

Живую проверку записи проводите только на вымышленной карточке в транзакции с полным откатом. Не изменяйте реальные доступы, не отправляйте письма и не выполняйте входы во внешнюю ФРДО ради выпуска. Отдельно фиксируйте, что проверено локально, что применено на сервере и какие инструменты обнаружены подключённым клиентом.
