Я проверил опубликованный домен `24zxc.ru`, сетевые запросы и текущую сборку. Главное отличие этого сайта от более простых сайтов: здесь на старте всё ещё есть несколько рискованных точек для Яндекс Браузера без VPN/при блокировках: тяжёлый `favicon.png` на 630 KB, внешние Google Fonts и Яндекс.Метрика после первого рендера, внешний backend-запрос за SEO-настройками, Lovable analytics script, а также `framer-motion` и декоративные анимации в первом чанке. В обычном Chrome это проходит, но в Яндексе на скриншоте видно именно сценарий: заголовок вкладки получил, HTML пришёл, но React-интерфейс не отрисовался — значит проблема на этапе загрузки/исполнения JS/CSS/внешних ресурсов.

План исправления:

1. Сделать «аварийный первый экран» прямо в `index.html`
- Добавить внутрь `#root` статический HTML-фолбэк: тёмный фон, логотип `24ZXC`, короткий текст/кнопки.
- Он будет виден сразу, даже если React-бандл, внешний скрипт или старый JS в Яндексе не выполнился.
- Когда React успешно загрузится, он автоматически заменит этот фолбэк нормальным сайтом.
- Это убирает белый экран как класс: пользователь больше не увидит пустую страницу.

2. Убрать рискованные внешние запросы с главной полностью, а не просто «лениво»
- Отключить Google Fonts на главной: оставить системные шрифты. Сейчас они загружаются после рендера, но в Яндексе без VPN даже отложенный запрос может висеть/мешать.
- Отключить `noscript`-пиксель Яндекс.Метрики из HTML, потому что он всё равно обращается к внешнему `mc.yandex.ru`.
- Оставить Метрику только через безопасную отложенную загрузку, но с дополнительным условием: не запускать её на слабом/проблемном окружении до полной интерактивности страницы.

3. Заменить тяжёлый favicon
- В `index.html` переключить favicon с `/favicon.png` на `/favicon.ico`.
- Сейчас `/favicon.png` весит около 630 KB, что ненормально для иконки вкладки. В профиле это один из самых тяжёлых и медленных ресурсов.
- PNG можно оставить как OG/запасной файл, но иконка браузера должна грузиться из лёгкого `.ico`.

4. Разорвать зависимость первого экрана от backend-запроса
- На главной SEO-настройки сейчас запрашиваются из backend-таблицы при загрузке.
- Сделать для главной статические значения по умолчанию и не ждать этот запрос для отображения.
- Backend-запрос можно оставить только как фоновое обновление метатегов, без влияния на первый экран.

5. Ещё сильнее разгрузить стартовый JS
- Убрать `framer-motion` из первого чанка главной там, где он используется только для декоративных элементов: `GeometricShapes`, `TropicalGlows`, `SectionDivider`, возможно `FlyingKey`/`InventoryBar`.
- Заменить стартовые декоративные motion-анимации на CSS-анимации или лениво грузить их после первого рендера.
- Оставить премиальный тёмный/золотой стиль, но не заставлять Яндекс исполнять лишний JS до появления первого экрана.

6. Добавить поддержку старых/капризных движков браузера
- Добавить `@vitejs/plugin-legacy` и `terser`.
- Настроить Vite так, чтобы сборка отдавала legacy/polyfill-вариант для старых Chromium-движков, включая старые версии Яндекс Браузера.
- Это закрывает риск, что конкретный Яндекс у пользователя не понимает часть современного JS из сборки.

7. Добавить диагностику без ломания интерфейса
- Поставить глобальный обработчик ошибок загрузки чанков/JS, чтобы при проблеме показывался понятный экран: «Не удалось загрузить скрипты, обновите страницу / включите совместимый режим», а не белая страница.
- Ошибку можно логировать в консоль, чтобы дальше точно понять, если у конкретного Яндекса блокируется какой-то файл.

8. Проверка после внедрения
- Проверить опубликованный/preview домен через сетевой профиль: первый экран должен появляться без Google Fonts, без тяжёлого favicon и без ожидания backend-запроса.
- Убедиться, что главная, навигация, скрытый вход в админку, ключи/сундук и визуальный стиль сохраняются.
- Если после этого конкретно в Яндексе пользователя проблема останется, следующий шаг будет уже не «оптимизация», а сбор точной ошибки через аварийный экран/console, потому что белого экрана больше быть не должно.
